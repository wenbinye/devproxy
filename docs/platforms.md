# Platform support and differences

## Directories and files

```
project root/
└── devproxy.toml     # project-level route declarations (optional, commit it, shared by the team)

~/.config/devproxy/
├── config.toml      # your configuration (optional; the tool does not generate it)
├── Caddyfile        # main config generated by the tool: global block + two imports
└── sites.caddy      # your personal sites -- the tool only imports it, never changes its contents

~/.local/state/devproxy/
├── routes.json      # the route table (the truth)
├── routes.caddy     # fragment deterministically rendered from routes.json, imported by the main Caddyfile
├── routes.lock      # flock while writing routes
├── caddy-storage.json   # storage archive left by migration (see above)
├── caddy-env.json       # unit environment-variable archive left by migration (e.g. MINIKUBE_IP)
├── dns-route.json       # hash of the DNS route contents last written
├── backups/             # backup directory (one timestamped subdirectory per migration)
└── logs/                # where service logs go on macOS
    └── routes/          # logs of background apps started by sync (<name>.log)

~/.local/share/caddy/    # Caddy storage: CA root certificate and issued certificates
```

**The route table is a file, not memory.** `routes.json` is the truth, and `routes.caddy` is its
deterministic rendering (the same table always produces byte-identical text); the main Caddyfile
`import`s this rendered artifact. Routes therefore **survive Caddy restarts**, and no resident daemon
is needed to keep them. Writing a route is a transaction: lock → modify the table → render →
`caddy validate` → write to disk → `caddy reload`; a failed reload rolls back what was written to disk.

---

| | Linux | macOS |
|---|---|---|
| Service unit | systemd user (`~/.config/systemd/user/`) | launchd: caddy via `/Library/LaunchDaemons/` (**root**), dnsmasq via `~/Library/LaunchAgents/` |
| Binding 80/443 | `setcap cap_net_bind_service=+ep` (needs `libcap2-bin`) | no setcap; relies on a root LaunchDaemon |
| DNS route | systemd-resolved drop-in or `/etc/dnsmasq.d/` | `/etc/resolver/<suffix>` |
| dnsmasq port | `5353` | `5300` (53 is taken by mDNSResponder) |
| dnsmasq binary | `/usr/sbin/dnsmasq` | not shipped with the system; requires Homebrew: fixed probe `/opt/homebrew/sbin` → `/usr/local/sbin` → `/usr/sbin` |
| CA trust | system trust store + NSS DB | system keychain |
| Start at login | `loginctl enable-linger` | launchd `RunAtLoad` (macOS has no linger concept) |
| Stop the caddy service | `systemctl --user stop caddy` | `launchctl bootout system/com.devproxy.caddy` |

**On macOS caddy runs as root**: this is the only clean way to bind 80/443 on macOS; the cost is that
all sites run with root privileges, and the CA, storage and logs leave files owned by root.

**The caddy version is pinned to 2.11.7**: the sha256 is hard-coded in the source, and setup verifies it
after downloading. The upstream release's `checksums.txt` does not match the assets actually served
(measured: both the tar.gz and the deb disagree), so the tool **does not trust** that file.

`devproxy selftest` starts an **isolated Caddy instance**: the admin / HTTPS / HTTP ports are all
**allocated dynamically at runtime** (fixed ports would fight over the same instance with concurrent
self-tests or with services already on your machine), with independent storage and an independent
config directory. It runs the full registration → forwarding → redirect → unregistration → certificate
policy sequence, **without touching the production 443/2019**, and without installing the sandbox CA
into the host's trust store.

## Environments without systemd: supervise with `devproxy run`

On Linux, `devproxy setup` supervises Caddy with **systemd user units**; on macOS it uses **launchd**.
Containers, WSL and minimal distributions often have neither -- then nobody supervises the routes
(the route table is a file, but **a Caddy process must load it**).

`devproxy run` is that host:

```bash
devproxy run                    # supervise Caddy in the foreground; Ctrl-C exits
devproxy run --config <path>    # load another Caddyfile (usually a different set of ports)
```

Its behaviour:

- **stdio goes straight to the terminal** -- Caddy's logs stream in real time (`devproxy logs caddy`
  follows the journal / log file; this takes over the process itself);
- **Ctrl-C exits cleanly** -- forwards SIGTERM to Caddy and waits for it to finish gracefully (at most
  10 seconds; force-kills only after the timeout), and devproxy exits 0;
- **installs no service and writes no state** -- foreground mode = leaves no trace (`routes.json` and
  the like are untouched).

Before starting there are three precondition checks (exit code **3** when unmet, with the platform's
corresponding fix command):

| Situation | Hint |
|---|---|
| Caddy binary missing | `devproxy setup` |
| Main Caddyfile missing | `devproxy setup` |
| **the live caddy service is still running** | Linux: `systemctl --user stop caddy`; macOS: `launchctl bootout system/com.devproxy.caddy` |

> The third check only applies when loading the **main Caddyfile** -- that is exactly what the service
> unit loads, so both would fight over the same ports. When `--config` points at another file it usually
> uses a different set of ports and should not be blocked; if ports really do collide, Caddy itself
> reports `address already in use`, which is more accurate than the tool's guess.

**How it differs from the other commands**:

| | `run` | `setup` | `selftest` | `logs caddy` |
|---|---|---|---|---|
| Supervision | foreground process | systemd / launchd service | foreground process (deleted after it runs) | none; only follows logs |
| Which config | the live main Caddyfile | — | **isolated** instance (temporary ports and storage) | — |
| Writes system state | no | installs a service, modifies /etc | no (everything in temporary directories) | no |
| After exit | routes are no longer served | routes stay up | nothing left behind | does not matter |
